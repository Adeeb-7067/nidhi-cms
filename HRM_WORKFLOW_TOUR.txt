1. EXECUTIVE SUMMARY
================================================================================

The HRM module is a full human-resources subsystem embedded inside the Content
Management Hub. It is NOT a standalone app — it shares CMS authentication,
role templates, permission matrix, navigation shell, and employee user records.

Core HR workflows implemented end-to-end:
  • Org structure (departments, employee directory, reporting lines)
  • Shift templates and per-employee shift assignment
  • Attendance via desktop work sessions (clock-in/out + heartbeats)
  • Daily attendance engine (present/late/absent/WFH/leave/holiday/weekend)
  • Leave requests with balance accrual, FIFO consumption, manager/HR approval
  • WFH requests with monthly limits and overlap checks
  • Company & department-scoped holidays
  • Attendance correction workflow
  • Payroll runs (generate → review → finalize → payslips → bank export)
  • HRM audit trail
  • Role-based dashboards (admin / manager / employee views)

Partially implemented (backend ready, UI placeholder):
  • Recruitment pipeline & onboarding tasks
  • Employee document upload/review
  • Policy library & employee acknowledgements
  • ID cards (permission module exists, no UI)

The module exposes ~60 REST endpoints under /api/hrm/* plus work-session
endpoints under /api/work-sessions/* that feed the attendance engine.

3. ACCESS CONTROL & SECURITY MODEL
================================================================================

THREE LAYERS OF ACCESS
----------------------

  Layer 1 — Route Role Gate (PageOutlet.tsx)
    Hard role lists per URL, e.g.:
      HRM_ADMIN_ROLES = super_admin, hr
      MONITORABLE_STAFF_ROLES = developer, designer, qa, ...
    Prevents wrong roles from even loading a page component.

  Layer 2 — Permission Gate (HrmGate / PermissionGate)
    Fine-grained module + action checks aligned with backend:
      module: "leave", action: "approve"
    Maps to CMS permission keys like hrm_leave:approve.

  Layer 3 — API Team Scoping (team-scope.js)
    Data-level restrictions even when route is accessible:
      • Employee sees only self
      • Manager sees self + direct reports (reportingManagerId)
      • HR admin / super_admin sees org-wide (null scope = all users)

TEAM SCOPE RULES (backend/src/services/hrm/team-scope.js)
-----------------------------------------------------------

  resolveScopedUserIds(req, userId?)
    • If userId query param provided → assertCanAccessUser → return [userId]
    • HR admin → null (all users)
    • Manager → [self, ...directReportIds]
    • Staff → [self]

  resolveAttendanceScopedUserIds(req, userId?)
    • Same pattern but uses canViewOrgAttendance (hrm_attendance:view permission)

  assertCanAccessUser(req, targetUserId)
    • Self always allowed
    • HRM admin role always allowed
    • hrm_employees:view permission → org-wide
    • Manager → only direct reports

  assertCanViewAttendanceForUser(req, targetUserId)
    • Self, org attendance viewers, or manager of direct report

LEAVE APPROVAL AUTHORITY (leave-approval.js)
--------------------------------------------
  • HR / super_admin can approve any leave request (override)
  • If requester has reportingManagerId → that manager may approve (final)
  • If no reporting manager → only HR / super_admin may approve
  • Requester cannot approve own request

WFH APPROVAL
------------
  Requires hrm_wfh:approve permission at API layer.
  Frontend shows approve/reject when user has permission.

PAYROLL PERMISSIONS
-------------------
  view, create, edit, finalize, export — separate actions on hrm_payroll module.
  Bank account numbers encrypted at rest (hrm-crypto.js, AES-GCM fields).

SENSITIVE DATA
--------------
  • Salary bank details: encrypted fields + masked display in API responses
  • Payslip PDF access: requires hrm_my_payslips:view
  • Audit log: hrm_audit:view only

PERMISSION MODULES (21 total)
-----------------------------
  Org/admin : dashboard, employees, departments, attendance, leave, wfh,
              shifts, holidays, payroll, roles, settings, audit,
              recruitment, documents, policies, id_cards
  Self      : my_attendance, my_leave, my_wfh, my_payslips, my_holidays

ACTIONS     : view, create, edit, delete, approve, finalize, export

5. END-TO-END PLATFORM WORKFLOWS
================================================================================

WORKFLOW A — NEW EMPLOYEE ONBOARDING (manual today)
---------------------------------------------------
  1. Admin creates user in CMS Team (/admin/employees)
  2. HR assigns department, reporting manager, WFH limit, accrual rate
     via /hrm/employees/:id (patch /api/hrm/users/:userId/profile)
  3. HR assigns shift template via /hrm/shifts
  4. HR sets salary structure via /hrm/payroll (structures tab)
  5. Employee clocks in via Electron/desktop work session
  6. Daily attendance materializes automatically
  7. Monthly leave accrual job credits EL balance
  (Recruitment module can automate steps 1-4 when UI is built)

WORKFLOW B — DAILY ATTENDANCE CYCLE
-----------------------------------
  1. Employee opens Electron app → POST /api/work-sessions/clock-in
  2. App sends heartbeat every N minutes → POST /api/work-sessions/heartbeat
  3. Employee clocks out → POST /api/work-sessions/clock-out
     OR session auto-ends (sleep, network loss, 24h limit, day rollover)
  4. Attendance materializer aggregates sessions → activeMinutes per work-day
  5. Attendance engine resolves status using:
       - Weekend days (company setting)
       - Holiday calendar
       - Approved leave (full or partial day)
       - Approved WFH or global WFH mode
       - Shift template (late detection via grace minutes)
       - Shortfall threshold (half_day / short status)
  6. Result stored in daily_attendance with source = "engine"
  7. HR/manager views in /hrm/attendance or employee in /hrm/my-attendance

WORKFLOW C — LEAVE REQUEST LIFECYCLE
------------------------------------
  1. Employee opens /hrm/leave or /hrm/my-leave
  2. Selects leave type, dates, day part (full/first_half/second_half/short)
  3. POST /api/hrm/leave/requests
     • Calculates working days (excludes weekends + holidays)
     • FIFO allocation across paid leave types (oldest accrual first)
     • Reserves balance: pending += days (optimistic locking via version field)
     • Notifies reporting manager + HR admins via realtime
     • Writes hrm_audit log entry
  4. Manager/HR reviews on /hrm/leave (pending tab)
  5. PATCH /api/hrm/leave/requests/:id { status: approved|rejected, reviewNote }
     • Approved: pending → used; attendance engine picks up on_leave days
     • Rejected: pending released back to available balance
  6. Employee sees updated balance and history

WORKFLOW D — WFH REQUEST LIFECYCLE
--------------------------------
  1. Employee submits date range + reason
  2. System checks:
     • Monthly WFH limit (per-user wfhMonthlyLimit, default 4)
     • No overlap with pending/approved leave on same dates
  3. Pending → manager/HR approves
  4. Approved WFH days resolve attendance status as "wfh" in engine
  5. Global WFH mode (company setting) bypasses individual requests

WORKFLOW E — ATTENDANCE CORRECTION
----------------------------------
  1. Employee or HR submits correction request with reason + desired status/minutes
  2. POST /api/hrm/attendance/corrections → status pending
  3. HR approver with hrm_attendance:approve reviews
  4. On approval: daily row updated with source = "manual_correction"
  5. Feeds into payroll paid/LOP day counts

WORKFLOW F — PAYROLL MONTH CLOSE
--------------------------------
  1. HR ensures attendance materialized for full month
  2. POST /api/hrm/payroll/runs { year, month } → creates draft run
  3. System generates lines per active employee:
     • Pulls salary structure (basic, HRA, allowances, PF, ESI, TDS)
     • Aggregates attendance: paidDays, lopDays, lateCount
     • Computes: dailyRate = gross/30, lopDeduction, net pay
  4. HR reviews checklist (blockers: missing structures, unfinalized prior month, etc.)
  5. HR edits individual lines if needed (PATCH /api/hrm/payroll/lines/:lineId)
  6. POST .../review → status reviewed
  7. POST .../finalize → status finalized, payslip records created
  8. Employees view slips at /hrm/my-payslips
  9. HR exports CSV / bank file (requires export permission)

WORKFLOW G — MONTHLY LEAVE ACCRUAL (background)
-----------------------------------------------
  1. Scheduled job runs ~02:00 local time (leave-accrual.service.js)
  2. Uses cross-process lock (withJobLock) to prevent duplicate runs
  3. For each active staff employee:
     • Credits EL (Earned Leave) by hrmPaidLeavesPerMonth or per-user override
     • At leave-year boundary: carry-forward unused days (if type allows)
  4. Leave year may start non-January (hrmLeaveYearStartMonth setting)

6.3 TIME & ATTENDANCE
--------------------------------------------------------------------------------

WORK SESSIONS (not under /hrm but core to attendance)
  POST /api/work-sessions/clock-in     (rate limited: 5/min)
  POST /api/work-sessions/clock-out
  POST /api/work-sessions/heartbeat
  GET  /api/work-sessions/active
  GET  /api/work-sessions/daily-totals
  GET  /api/work-sessions
  POST /api/work-sessions/:sessionId/terminate  (super_admin only)

  Stop reasons tracked: clock_out, day_ended, client_disconnected, session_expired,
  system_sleep, network_lost, app_quit, logout, admin_terminated

  hrmElectronOnlyClock setting: when true, only Electron client may clock in.

ATTENDANCE ENGINE (attendance-engine.js)
  Status resolution priority:
    1. Weekend (company hrmWeekendDays setting, default Sat-Sun)
    2. Holiday (company or department scoped)
    3. Full-day approved leave → on_leave
    4. Partial-day leave + no clock → on_leave (partial)
    5. WFH (approved request OR global WFH mode) → wfh
    6. Clock time vs shift → present | late | absent | short | half_day

  Compliance field: met | short | absent | exempt

  Missing clock-out detection flags sessions auto-closed without manual clock-out.

DAILY ATTENDANCE API
  GET /api/hrm/attendance/daily?startDate&endDate&userId&departmentId
  Returns HrmAttendanceSummary[] with:
    userId, userName, date, status, expectedMinutes, activeMinutes,
    varianceMinutes, sessionCount, corrected, missingClockOut, etc.

ATTENDANCE PAGE (/hrm/attendance)
  • Date range picker + department filter
  • KPI row: present, absent, on leave, WFH, late counts
  • Table with status badges, variance highlighting
  • Variance tab (requires hrm_attendance:view): flagged rows where
    logged hours vs clock hours exceed threshold
  • Corrections tab: submit/review correction requests

MY ATTENDANCE (/hrm/my-attendance)
  Re-exports Attendance.tsx — same component, scoped to logged-in user.

6.4 LEAVE MANAGEMENT
--------------------------------------------------------------------------------

LEAVE TYPES (seeded)
  Multiple types with fifoPriority, maxDaysPerYear, isPaid, carryForwardAllowed.
  Primary accrual type code: EL (Earned Leave).

DAY PARTS
  full         — multi-day range, counts working days only
  first_half   — 0.5 day, single date
  second_half  — 0.5 day, single date
  short        — 0.25 day, single date

BALANCE MODEL
  Per user, per leave type, per leave-year:
    allocated, used, pending, carriedForward, version (optimistic lock)

FIFO CONSUMPTION (leave-accrual.service.js → allocateOldestFirst)
  When request spans multiple days, system allocates from lowest fifoPriority
  paid leave types first. Overflow → unpaid (LOP).

LEAVE PAGE (/hrm/leave)
  Admin/manager view:
    • Tabs: Pending | History | Balances (admin)
    • KPI: pending, approved, rejected, total
    • Inline approve/reject with review note
  Staff without admin view:
    • Sees own requests only (same page, scoped queries)

API
  GET  /api/hrm/leave/types
  GET  /api/hrm/leave/balances?userId&year
  GET  /api/hrm/leave/requests?userId&status&date
  POST /api/hrm/leave/requests
  PATCH /api/hrm/leave/requests/:id  (requires hrm_leave:approve)

MY LEAVE (/hrm/my-leave)
  Dedicated self-service page for apply + history + balances.

6.8 PAYROLL
--------------------------------------------------------------------------------

SALARY STRUCTURE (per employee)
  basic, hra, allowances, pfEmployee, pfEmployer, esiEmployee, tds
  gross = sum of earnings; net = gross - deductions
  Bank fields encrypted (PAN, account, IFSC, bank name)

PAYROLL RUN STATUSES
  draft → reviewed → finalized → paid

COMPUTATION (payroll-compute.js)
  paidDays  : present, late, wfh, holiday, on_leave (compliance != absent)
  lopDays   : absent or short compliance
  lateCount : status === late
  lopDeduction = (gross / 30) * lopDays
  net = gross - statutory deductions - lopDeduction

PAYROLL PAGE (/hrm/payroll)
  • Period selector (year/month)
  • Generate run, review, finalize actions
  • Lines table with inline edit, paid/pending filter
  • Salary structures dialog (upsert per employee)
  • Export CSV + bank export download links
  • Disbursement progress widget
  • KPI: employee count, gross, net, paid vs pending

MY PAYSLIPS (/hrm/my-payslips)
  • Lists finalized slips for logged-in user
  • Opens PDF via GET /api/hrm/payslips/:id (direct fetch + toast on error)

READINESS CHECKLIST
  GET /api/hrm/payroll/runs/:id/checklist
  Blockers prevent finalize until resolved (evaluatePayrollReadiness).

9. BACKGROUND JOBS & AUTOMATION
================================================================================

LEAVE ACCRUAL JOB (leave-accrual.service.js)
  • Runs on interval tick (5 min) checking local hour == LEAVE_ACCRUAL_RUN_HOUR (2 AM)
  • Uses withJobLock for single-runner guarantee across processes
  • Credits monthly EL, handles year-end carry-forward
  • Per-user override via users.leaveAccrualDaysPerMonth

ATTENDANCE MATERIALIZATION
  • On-demand when querying daily attendance for today or missing rows
  • computeUserDaySummary + materializeUserAttendanceDay
  • Combines work sessions + policy context (shift, leave, WFH, holiday)

REALTIME EVENTS
  • broadcast("hrm_leave_updated"), broadcast("hrm_wfh_updated")
  • Work session end → notifyUser + FCM push with human-readable reason

SEED SCRIPT (npm run from backend/scripts/seed-hrm-defaults.mjs)
  • ensureDefaultRoleTemplates()
  • seedLeaveTypes()
  • seedDefaultShift()
  • Sets hrmDefaultShiftTemplateId in company settings
