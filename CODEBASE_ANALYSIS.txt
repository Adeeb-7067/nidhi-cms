1. EXECUTIVE SUMMARY
================================================================================

Content Management Hub (CMS) is a full-stack client and project management
platform built for software agencies. It helps teams manage client projects,
track bugs, log daily work, distribute APK/IPA builds, maintain project
inventory (credentials, assets, subscriptions), communicate via discussions,
handle support tickets, and generate analytics reports.

The system is split into three independently deployable applications:

  • Backend  — Express 5 REST API + Socket.IO realtime (port 8080)
  • Frontend — React 19 SPA built with Vite (port 5173)
  • Electron — Native desktop wrapper (Windows + macOS) for the frontend

Typical production deployment uses two domains:
  app.example.com  (static frontend)
  api.example.com  (Node.js API + WebSockets)

The Electron desktop app connects to the same remote backend — it wraps only
the frontend in a native shell (shell architecture, no embedded backend).

Twelve CMS login roles drive identity, home redirects, and data scoping,
plus a CMS-wide permission matrix (role templates):

  super_admin, hr, manager, developer, tester, qa, client, freelancer,
  bde, finance, digital, ca

Access is controlled by TWO layers (see Section 6a):
  1. CMS login role (user.role) — identity, defaults, data scoping, home URL
  2. Permission template (roleTemplateId) — module×action matrix (primary)

Backend is a domain modular monolith under backend/src/modules/ (19 domains).
~1,298 inventoried source files; graphify ~16k nodes; code-review-graph
~509 indexed files / 2.4k nodes (auto-updated on code changes).

Core live features (backend-integrated):
  Projects (development | maintenance | digital), Bugs, Daily Logs, Tasks,
  APK Releases, Discussions/Comments, Tickets, Resource Requests,
  Inventory Vault, Analytics, Reports, Notifications, Presence,
  Client Portal, Employee Management, Screenshot Monitoring (private
  uploads + content proxy), Attendance / work sessions, HRM (full suite),
  Sales/CRM, Finance (expenses, vendors, ledgers, tax, loans, …),
  Marketing / Digital hub, Legal department API, CA compliance workbench
  (tasks, notices, GST/TDS/ITR/ROC surfaces, bank-statement recon).

2. WHAT THIS PROJECT IS
================================================================================

PURPOSE
-------
CMS is an internal operations platform for a software development agency.
It centralizes everything needed to deliver client projects:

  • Project lifecycle management (scoping → UAT → completed → maintenance)
  • Quality assurance (bug tracking with dual QA/dev workflow)
  • Developer accountability (daily work logs with compliance enforcement)
  • Client transparency (portal, visible discussions, APK downloads)
  • Asset management (encrypted credentials, environments, subscriptions)
  • Team coordination (tasks, tickets, resource requests, realtime chat)
  • Business intelligence (dashboards, PDF/Excel reports)
  • Staff monitoring (screenshot capture, attendance — Electron + admin views)
  • Business ops prototypes (Sales, Finance, Legal, CA mock UI panels)

TARGET USERS
------------
  Super Admin  — Agency owner; full system control; manages roles & permissions
  HR           — HRM admin; default hr_admin template (matrix-configurable)
  Manager      — Team lead; HRM approve + dev portal
  Developer    — Builds software; logs work, fixes bugs
  Freelancer   — External contractor; dev-portal access
  Tester/QA    — Reports and triages bugs
  BDE          — Sales pipeline, proposals, CRM
  Client       — Views project progress, downloads APKs, raises tickets

BUSINESS DOMAIN
---------------
Software agency delivering mobile/web apps to client companies.
Each client company has multiple projects. Each project has a team,
bugs, logs, releases, inventory, and discussion channels.

ROLES (CMS login roles — user.role field)
--------------------------------------------
  super_admin  — Break-glass full access; bypasses permission matrix
  hr           — HR staff; default template hr_admin (not auto-bypass anymore)
  manager      — Team lead; default template manager
  developer    — Project team; default template employee
  tester, qa   — QA staff; default template employee
  freelancer   — External contractor; default template employee
  bde          — Business development; default template bde
  finance      — Finance staff; home /finance; employee-ID login
  digital      — Digital/marketing specialist; home /marketing; digital projects only
  ca           — Chartered-accountant workbench; home /ca

LOGIN METHODS
-------------
  super_admin, client, hr  → Login with EMAIL + password
  developer, tester, qa, freelancer, manager, bde, finance, digital, ca
                           → Login with EMPLOYEE ID (e.g. AL001) + password

USER STATUSES: active | inactive | suspended

CMS ROLE vs PERMISSION TEMPLATE (two-layer model)
-------------------------------------------------
  CMS role (user.role)              | Permission template (roleTemplateId)
  ----------------------------------|----------------------------------------
  Required on every account         | Optional; "Default for role" if null
  Login home redirect               | Sidebar + page access (mapped routes)
  BDE own-leads data scoping        | API requirePermission checks
  Digital → digital projects only   | Button-level PermissionGate (partial)
  Manager team scoping (team-scope) | HRM/Sales/Finance/CA/Marketing visibility
  Employee ID generation            |
  Profile page variant              |

  Resolution order for effective permissions:
    1. Explicit roleTemplateId on user document
    2. defaultTemplateByRole[user.role] → template code → DB id
    3. Template where cmsRole === user.role

  Managed on: Admin → Roles & permissions (/admin/roles or /hrm/roles)
  Assigned on: Admin → Team form → "Permission template" field

DEFAULT SYSTEM TEMPLATES (backend seeds + backfill on boot)
------------------------------------------------------------
  super_admin    — All modules × all actions (grants: "all")

6a. ROLES & PERMISSIONS MATRIX (CMS RBAC) — CURRENT STATUS
================================================================================
Last updated: July 31, 2026

OVERVIEW
--------
Super admin configures access via Admin → Roles & permissions. Each role
template stores rows of (module, action). Users receive a template via Team
form (explicit roleTemplateId) or default mapping from CMS role.

WHAT THE MATRIX CONTROLS (implemented)
--------------------------------------
  ✓ Sidebar visibility (canViewHref on mapped routes)
  ✓ Page access (RoleGate → resolveRoutePermission → usePermission)
  ✓ In-page gates (PermissionGate, usePermission hook)
  ✓ HRM / Sales / Finance / Marketing / CA / Legal API permission gates
  ✓ Roles API (requirePermission roles_permissions view/edit)
  ✓ Monitoring attendance route (monitor_attendance module)
  ✓ Template CRUD + batch save on Roles page
  ✓ Permission validation on PATCH (catalog enum check)
  ✓ Transactional template permission replace (runInTx)
  ✓ Cache eviction on template change (30s backend, 30s frontend stale)
  ✓ Roles finance / digital / ca in userRoles + frontend mirrors + tests

WHAT STILL USES CMS ROLE / HARDCODED LOGIC (not fully matrix-driven)
--------------------------------------------------------------------
  ✗ super_admin — always bypasses matrix (by design)
  ✗ client portal — separate client role boundary
  ✗ Projects, bugs, tasks, logs, tickets, users APIs — mostly requireAuth
    only; membership/role checks in controllers (not requirePermission)
  ✗ BDE data scope — sales controllers filter by req.user.role === "bde"
  ✗ Digital create/list — role === "digital" forces type digital projects
  ✗ Manager team scope — team-scope uses role === "manager"
  ✗ Login home URL — getHomeHref(role) not template-based
  ✗ Many in-page buttons — still check user.role === "super_admin"
  ✗ Data scope flags — no per-template org/team/self scope on Roles page

7. AUTHENTICATION & SECURITY
================================================================================

AUTH FLOW
---------
  1. POST /api/auth/login
     → Validates credentials (email OR employee ID)
     → Returns access token (15 min) + refresh token (30 days)
     → Creates session row in Sessions collection

  2. Protected requests
     → Authorization: Bearer <accessToken> OR X-Access-Token header
     → requireAuth middleware verifies JWT, loads user, rejects inactive

  3. Token refresh
     → POST /api/auth/refresh with refresh token
     → Validates refresh JWT + session row
     → Issues new access token

  4. Logout
     → POST /api/auth/logout
     → Deletes session by refresh token

  5. Frontend auto-refresh
     → custom-fetch.ts transparently refreshes on 401
     → Queued refresh prevents thundering herd
     → Events: cms:auth-token-refreshed, cms:auth-session-expired

PASSWORD MANAGEMENT
-------------------
  Forgot password  → OTP email (10 min TTL, attempt limits)
  Change password  → In-app OTP request + verification
  Admin reset      → super_admin can reset any user's password
  Credential history → Encrypted password storage for admin-managed accounts

IMPERSONATION
-------------
  super_admin can "view as" another user via POST /api/auth/impersonate/:userId
  Frontend stores impersonation tokens separately (lib/impersonation-storage.ts)
  Banner shown during impersonation; stop restores admin tokens

RATE LIMITING (auth routes)
---------------------------
  Login          : 10 requests / 15 min
  Forgot password: 5 requests / hour
  Verify OTP     : 30 requests / 15 min
  Reset password : 10 requests / 15 min
  Refresh token  : 30 requests / 5 min

SECURITY MIDDLEWARE
-------------------
  helmet         → Security headers
  cors           → ALLOWED_ORIGINS whitelist
  express-rate-limit → Auth brute-force protection
  audit middleware → Logs POST/PUT/PATCH/DELETE mutations

PUBLIC API PATHS (no auth required)
------------------------------------
  GET  /api/healthz
  POST /api/auth/login
  POST /api/auth/refresh
  POST /api/auth/forgot-password
  POST /api/auth/verify-reset-otp
  POST /api/auth/reset-password

ERROR FORMAT (consistent across API)
------------------------------------
  { "error": "Human message", "code": "NOT_FOUND", "field": "email" }

================================================================================

SOCKET.IO (backend/src/lib/realtime.js)
---------------------------------------
  Path: /socket.io on same port as HTTP
  Auth: Client sends auth.token (access JWT) + query.userId
  Rooms: user:{userId} for targeted delivery

Events (server → client):
  notification     — New in-app notification (+ FCM push)
  comment          — New/updated comment in subscribed threads
  ticket_update    — Ticket status/assignment change
  request_update   — Resource request status change
  presence:update  — User online/away/offline change
  inventory:*      — Inventory changes (broadcast)

Events (client → server):
  presence:heartbeat — Tab visibility + activity ping

Helper functions:
  notifyUser(userId, event, data)   — Targeted emit + FCM

19. DATA FLOW DIAGRAMS
================================================================================

LOGIN FLOW
----------
  User → /login page
    → POST /api/auth/login (email or employee ID + password)
    → Returns { accessToken, refreshToken, user }
    → AuthContext stores tokens in localStorage
    → useGetMe fetches profile
    → Redirect to role home (/admin, /dev, or /client)
    → RealtimeProvider connects Socket.io
    → PresenceProvider starts heartbeat

BUG REPORT FLOW
---------------
  QA/Tester → Dev Bugs page or Project Hub Bugs tab
    → bug-form-dialog.tsx (title, description, severity, attachments)
    → POST /api/bugs (or POST /api/bugs/batch for multiple issues)
    → bug-workflow.js validates creator role
    → Creates Bugs document + optional issues[]
    → notifyUser to project members
    → Socket.io 'notification' to relevant users
    → TanStack Query cache invalidated

  Assignment:
    QA → PATCH /api/bugs/:id/assign { assigneeId }
    → work-assignments.js validates assignee is project member
    → Notification to assigned developer

  Resolution:
    Developer → PATCH /api/bugs/:id { devStatus: "fixed" }
    QA → PATCH /api/bugs/:id { qaStatus, finalStatus }
    → Role-gated in bug-workflow.js

DISCUSSION MESSAGE FLOW
-----------------------
  User → Discussions page or Project Hub Comments tab
    → discussion-chat-panel.tsx → chat-composer.tsx
    → Optional: @mention, emoji, voice, file attachment
    → POST /api/comments { threadType, threadId, body, attachments }
    → comment-mentions.js parses @mentions
    → comment-notification-recipients.js resolves targets
    → Creates Comments document
    → emitToUsers with 'comment' event
    → Frontend: discussion-realtime.ts updates query cache
    → Unread state tracked in discussions-read-state.ts

DAILY LOG COMPLIANCE FLOW
-------------------------
  Developer → /dev/logs → create/edit log entries
    → POST/PATCH /api/logs { projectId, date, hours, description }

  Background (every 5 min at configured hour):
    → daily-log-compliance.js runs
    → For each active staff member:
        Sum today's log hours vs requiredDailyWorkHours
    → If incomplete:
        Create log_compliance notification
        emitToUsers via Socket.io
        sendDailyLogComplianceEmail via SMTP

APK RELEASE FLOW
----------------
  Developer → /dev/apk or Project Hub Releases tab
    → Upload file via POST /api/upload?category=apk
    → POST /api/projects/:id/apk-releases { version, audience, fileUrl }
    → apk-access.js applies audience rules
    → Client downloads via GET /api/apk-releases/:id (filtered by role)

INVENTORY CREDENTIAL REVEAL FLOW
--------------------------------
  Developer/Admin → Project Hub Inventory → Credentials
    → POST /api/projects/:id/inventory/credentials/:id/reveal
    → guardInventoryAccess checks permissions
    → inventory-crypto.js decrypts AES-256-GCM secret

24. ELECTRON DESKTOP APP
================================================================================

ARCHITECTURE DECISION: SHELL MODE
-----------------------------------
The Electron app wraps only the React frontend in a native window. The backend
remains deployed remotely and is NOT embedded in the desktop package.

Rationale:
  • App is multi-user — MongoDB Atlas and background jobs must run 24/7 on server
  • Socket.IO presence requires a shared server
  • Embedding backend adds complexity with zero offline benefit
  • Shell architecture keeps the packaged binary small (~150 MB)

MAIN PROCESS (electron/main.js)
---------------------------------
Responsibilities:
  • Single-instance lock (prevents duplicate windows)
  • BrowserWindow: 1280×800, min 900×600, show:false until ready-to-show
  • Security: contextIsolation=true, nodeIntegration=false, sandbox=true
  • Menu bar removed: Menu.setApplicationMenu(null)
  • CSP injected via session.defaultSession.webRequest.onHeadersReceived
  • Media redirect: file:///uploads/* → {API_URL}/uploads/* via onBeforeRequest
  • External link handling: setWindowOpenHandler + will-navigate → shell.openExternal
    (URL scheme validated: only http/https pass through to OS browser)
  • Tray icon with context menu (Open / Quit); close button hides, doesn't quit
  • Second-instance handler re-focuses existing window
  • Auto-updater (electron-updater, lazy-loaded after app.whenReady)
  • Error dialog if frontend build is missing (did-fail-load handler)

KEY PATH CONSTANTS
  API_URL       CMS_API_URL env var (set by launch.js from frontend/.env)
  FRONTEND_DIST dev:       ../frontend/dist/electron/
                packaged:  {resourcesPath}/frontend/dist/electron/
  PRELOAD_PATH  __dirname/preload.js (works in both dev and ASAR)
  ASSETS_DIR    dev:       ./assets/
                packaged:  {resourcesPath}/electron/assets/

PRELOAD SCRIPT (electron/preload.js)
--------------------------------------
Exposes window.electron via contextBridge (renderer cannot access Node APIs).

  window.electron = {
    platform          — process.platform ('win32' | 'darwin' | 'linux')
    openExternal(url) — open URL in OS browser (validated http/https only)
    getAppVersion()   — returns packaged app version string
    showOpenDialog()  — native file picker dialog
    checkForUpdates() — manually trigger update check
    quitAndInstall()  — apply downloaded update
    onUpdateAvailable(cb) → returns unsubscribe fn
    onUpdateDownloaded(cb) → returns unsubscribe fn
  }

DEV LAUNCHER (electron/launch.js)
-----------------------------------
Problem: VS Code is itself Electron. It sets ELECTRON_RUN_AS_NODE=1, which
causes child Electron processes to run in Node.js mode (require('electron')
returns binary path string, not Electron APIs).

Fix: launch.js deletes ELECTRON_RUN_AS_NODE from env before spawning Electron,
and reads VITE_API_BASE_URL from frontend/.env to pass as CMS_API_URL.

Packaged builds: electron/scripts/write-api-config.js writes
electron/assets/api-config.json at build time so screenshot uploads and
API calls use the production URL (not localhost default in main.js).

  node launch.js
    → delete env.ELECTRON_RUN_AS_NODE
    → read frontend/.env → CMS_API_URL
    → spawn electron . with clean env

FRONTEND ELECTRON BUILD (frontend/electron.vite.config.ts)
------------------------------------------------------------
Separate Vite config — does NOT affect npm run build (web):
  base: './'              Assets use relative paths (required for file://)
  outDir: dist/electron/  Separate from web dist/public/ (no overwrite risk)
  VITE_ELECTRON=true      Baked in — activates hash routing in App.tsx
  VITE_APP_LOGO=./logo.png  Overrides /logo.png (absolute path breaks file://)
  VITE_API_BASE_URL       Set at build time for production Electron builds

FRONTEND ADAPTATIONS FOR ELECTRON
------------------------------------
All changes are runtime-gated on window.electron — zero effect on web browser.

  App.tsx
    isElectron() → useHashLocation hook + base="" for WouterRouter
    Hash routing is required: file:// context has no history API for path routing

  lib/electron-bridge.ts
    isElectron()            — window.electron !== undefined
    openExternal(url)       — IPC or window.open fallback
    getLocationSearch()     — reads ?params from hash fragment in Electron,
                              from window.location.search in browser
    clearLocationParam(key) — removes param from hash (Electron) or search (web)

  lib/firebase.ts
    Returns null in Electron — FCM requires HTTPS, file:// context unsupported
    Native window.Notification() still works for in-app alerts

  contexts/AuthContext.tsx
    bootstrap() wrapped in try/catch — network error on startup clears stale
    session and navigates to login (prevents infinite loading screen)

  lib/notification-navigation.ts + discussions-navigation.ts

    All use getLocationSearch() — deep-links from notifications work correctly
    with hash routing (#/dev/bugs?bug=5 instead of /dev/bugs?bug=5)

  pages/settings/SettingsPage.tsx
    goToSection() skips replaceState when hash starts with #/ (would overwrite
    the route fragment with a section name)

  components/ui/sidebar.tsx
    Sidebar state reads from cookie first (web), then localStorage (Electron).
    Writes to both on every toggle. Sidebar open/collapsed state now persists
    across restarts in both web and Electron.

  components/UpdateNotificationBanner.tsx
    Registers onUpdateAvailable / onUpdateDownloaded listeners.
    Shows Sonner toast with "Restart now" button calling quitAndInstall().
    Returns null — no DOM output.

BACKEND CORS FIX (backend/src/config/env.js)
----------------------------------------------
Electron's file:// renderer sends Origin: null on all API requests.
getAllowedOrigins() was updated to accept null origin:

  return (origin, callback) => {
    if (!origin || origin === "null" || origins.includes(origin)) {
      callback(null, true);   // allow Electron + configured origins
    } else {
      callback(null, false);  // clean rejection (no error propagation)
    }
  };

  ✓ Socket.io realtime (connects to remote backend)
  ✓ JWT auth + token refresh
  ✓ localStorage (tokens, theme, sidebar state)
  ✓ All feature pages (bugs, logs, discussions, inventory, etc.)
  ✓ File uploads (XHR via apiUrl() — absolute URL)
  ✓ navigator.clipboard (fully supported in Electron)
  ✓ navigator.mediaDevices.getUserMedia (voice recording)
  ✓ Native window.Notification() (OS-level toasts)
  ✓ jsPDF client-side reports
  ✓ Lottie animations, charts, all UI components
  ✓ Notification deep-links (?bug=5, ?ticket=3, ?project=2)
  ✓ Discussions channel pre-selection from notifications

WHAT BEHAVES DIFFERENTLY
--------------------------
  • Firebase FCM push         — Disabled (file:// unsupported). Native
                                window.Notification still fires for in-app alerts
  • External links            — Open in OS browser (Chrome/Edge/Safari)
                                via shell.openExternal, not a new Electron window
  • Report file downloads     — Open in OS browser (intercepted same way)
  • Settings section URL hash — Skipped in Electron (hash is the route itself)
  • Service worker            — Not registered (Firebase SW guard prevents it)

LOCAL DEV WORKFLOW
-------------------
  # Terminal A — backend
  cd backend && npm run dev

  # Terminal B — build frontend for Electron (once; re-run after UI changes)
  cd frontend
  set VITE_API_BASE_URL=http://localhost:15000
  npm run build:electron

  # Terminal C — launch Electron
  cd electron && npm run dev

PRODUCTION INSTALLER BUILD
----------------------------
  # Set API URL before building (required for screenshot uploads on other PCs)
  cd electron
  set VITE_API_BASE_URL=https://api.yourdomain.com
  npm run build:win     → dist-electron/CMS Desktop Setup 1.0.0.exe

  # macOS (.dmg)
  npm run build:mac     → dist-electron/CMS Desktop-1.0.0.dmg

  write-api-config.js runs automatically via npm run build:win — embeds
